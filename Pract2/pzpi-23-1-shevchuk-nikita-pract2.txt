3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Загальні відомості про систему
Назва системи: Spotify (цифрова платформа потокового аудіо).
Розробник: Стокгольмська компанія Spotify Technology S.A.
Призначення системи: Надання послуг легального стримінгу музичних треків, подкастів та відеоматеріалів із застосуванням технологій інтелектуальних рекомендацій. Цільова аудиторія охоплює понад 600 мільйонів активних користувачів щомісяця у 180 країнах світу. Основна функціональність полягає у миттєвому відтворенні аудіоконтенту з медіатеки обсягом понад 100 мільйонів композицій без буферизації.
3.2 Архітектурний стиль системи
Платформа Spotify побудована на основі децентралізованого мікросервісного архітектурного стилю, інтегрованого з подієво-орієнтованими підходами.
Обґрунтування вибору архітектури: Перехід від початкового моноліту до мікросервісів зумовлений критичною потребою забезпечення горизонтального масштабування під мільйонні одночасні сесії та організаційною структурою інженерних команд. Автономність кожного окремого сервісу (загалом понад 3000) мінімізує зону потенційного збою та дозволяє незалежно розгортати нові функції.
3.3 Основні компоненти системи
Організаційна структура містить такі рівні та підсистеми:
– Інтерфейс користувача: кросплатформні клієнтські додатки (Web, Android, iOS, Desktop), які взаємодіють із сервером через єдину точку входу;
– Серверна частина та рівень бізнес-логики: мережа автономних сервісів Apollo API Gateway, сервіси керування плейлистами, профілями, авторизацією та підписками, розгорнуті в хмарі Google Cloud Platform;
– Рівень зберігання даних: гібридна модель, де NoSQL СУБД Apache Cassandra використовується для профілів та плейлистів, Google Cloud Bigtable та Cloud Storage — для медіафайлів (blobs), а аналітична платформа BigQuery — для обробки історичних даних;
– Допоміжні сервіси: системи рекомендацій на базі машинного навчання, шина подій Apache Kafka та сервіси моніторингу.
3.4 Взаємодія компонентів
Внутрішня взаємодія між мікросервісами реалізована за допомогою високопродуктивного бінарного протоколу gRPC поверх HTTP/2, що суттєво знижує затримки та забезпечує сувору типізацію контрактів. Реєстрація дій користувача, таких як прослуховування чи уподобання відбувається асинхронно через розподілену шину повідомлень Apache Kafka. Глобальна доставка аудіо-потоків без затримок досягається через мережі CDN (Content Delivery Network), де зашифровані аудіо-чанки кешуються безпосередньо на Edge-серверах у максимальній географічній близькості до клієнта.
3.5 Масштабованість та надійність
Горизонтальна масштабованість забезпечується динамічною оркестрацією контейнерів у хмарі Google Cloud. Відмовостійкість системи гарантується реплікацією даних у Cassandra між декількома географічними зонами (Multi-Region deployment). Навантаження балансується на рівні шлюзів Apollo Gateway, які розподіляють потоки запитів. Використання технології Edge Caching повністю нівелює навантаження на основні бази даних під час стримінгу популярних треків.
3.6 Приклади програмної реалізації
Архітектурні принципи екосистеми моделюються за допомогою об'єктно-орієнтованих абстракцій на мові програмування Python. Розроблено архітектурні модулі, які симулюють поведінку шлюзу API Gateway з маршрутизацією та кешуванням на рівні CDN, а також асинхронне логування телеметрії прослуховувань у брокер повідомлень Kafka. Повний текст реалізації наведено у відповідному додатку.

	Внесок автора: аналіз масштабів платформи Spotify, формулювання критеріїв оцінювання архітектурних стилів, критичний аналіз відповіді ШІ та адаптація отриманих даних до структури підрозділу 3.2 звітного документа, порівняльний аналіз реляційних та NoSQL рішень під різні типи навантажень, постановка технічного завдання для ШІ щодо оптимізації шару збереження даних, інтеграція аналітичних висновків у підрозділи 3.3 та 3.5 звіту.	
	Запит: Проаналізуй архітектуру Spotify. Поясни, чому компанія перейшла від монолітної системи до децентралізованих мікросервісів, які архітектурні стилі тут поєднуються та як це пов'язано з організаційною структурою інженерних команд. Подай відповідь в академічному стилі. 
	Відповідь: Платформа Spotify використовує комбінацію мікросервісного (Microservices Architecture) та подієво-орієнтованого (Event-Driven Architecture) архітектурних стилів. Історичний перехід від монолітної архітектури, здійснений у період активного зростання бази користувачів, був зумовлений потребою знизити рівень зачеплення (coupling) компонентів та розширити можливості горизонтального масштабування. Наразі екосистема налічує понад 3000 автономних мікросервісів, кожен з яких інкапсулює окрему бізнес-функцію (пошук, рекомендації, білінг тощо). Цей розподіл безпосередньо корелює з організаційною моделлю інженерних команд (Spotify Squad Model): кожна автономна група (squad) повністю володіє своїм мікросервісом, забезпечуючи його розробку, розгортання та експлуатацію, що мінімізує зону потенційного збою (blast radius) системи в цілому.
	Запит: Опиши гібридну модель збереження даних у Spotify. Які саме бази даних використовуються під різні типи контенту і яку роль відіграє Apache Kafka в асинхронній реєстрації подій для сервісу Spotify Wrapped? 
	Відповідь: Сховище даних Spotify базується на принципах поліглот-персистенції (Polyglot Persistence) для оптимізації під конкретні типи навантажень. Метадані користувачів та динамічні структури плейлистів зберігаються в розподіленій NoSQL СУБД Apache Cassandra, що забезпечує лінійне горизонтальне масштабування та високу доступність без єдиної точки збою. Важкі медіафайли (аудіо-blobs) зберігаються у хмарних об'єктах Google Cloud Storage (GCS) та Bigtable, оптимізованих під швидке читання. Для реєстрації мільярдів щоденних подій (лайки, прослуховування) розгорнуто розподілену шину повідомлень Apache Kafka. Вона функціонує як асинхронний буфер (Event Bus), накопичуючи логи телеметрії без блокування клієнтських запитів. Згодом ці дані пакетно імпортуються до аналітичного сховища Google BigQuery, де алгоритми машинного навчання обробляють петабайти інформації для генерації персоналізованих рекомендацій та щорічних звітів Spotify Wrapped.

1  import time
2  from typing import Optional
3  
4  class SpotifyCdnEdgeCache:
5      def __init__(self) -> None:
6          self._cached_chunks: dict[str, bytes] = {}
7  
8      def get_audio_chunk(self, track_id: str) -> Optional[bytes]:
9          return self._cached_chunks.get(track_id)
10  
11      def cache_track(self, track_id: str, data: bytes) -> None:
12          self._cached_chunks[track_id] = data
13  
14  class ApolloApiGateway:
15      def __init__(self, cdn_node: SpotifyCdnEdgeCache) -> None:
16          self._cdn = cdn_node
17          self._central_storage: dict[str, bytes] = {
18              "track_404": b"[BinaryAudioData_Track404]",
19              "track_777": b"[BinaryAudioData_Track777]"
20          }
21  
22      def route_stream_request(self, user_id: str, track_id: str) -> bytes:
23          cached_data = self._cdn.get_audio_chunk(track_id)
24          if cached_data:
25              return b"CDN_EDGE_SUCCESS: " + cached_data
26          
27          raw_data = self._central_storage.get(track_id, b"")
28          if raw_data:
29              self._cdn.cache_track(track_id, raw_data)
30              return b"CENTRAL_CLOUD_FETCH_SUCCESS: " + raw_data
31          return b"ERROR: TRACK_NOT_FOUND"
32  
33  class KafkaAnalyticsEventBus:
34      def __init__(self) -> None:
35          self._topic_telemetry: list[dict] = []
36  
37      def publish_listen_event(self, user_id: str, track_id: str) -> None:
38          event = {
39              "timestamp": time.time(),
40              "user_id": user_id,
41              "track_id": track_id,
42              "action": "play_completed"
43          }
44          self._topic_telemetry.append(event)
45  
46      def get_logged_events(self) -> list[dict]:
47          return self._topic_telemetry
